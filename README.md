# Bustler Revision Assistant

A lightweight revision-brief workflow for Bustler with customer and provider views, token-based brief access, and a minimal Node + Firestore backend.

## What It Does

- Customers can convert raw feedback into a structured revision brief.
- Each approved brief gets a token-backed provider link.
- Only the linked customer and assigned provider can access that brief.
- Providers can update progress, complete tasks, and work through multiple revision rounds on the same brief thread.

## Current Architecture

- Frontend: plain HTML, CSS, and JavaScript
- Backend: Express in `backend/server.js`
- Database: Firebase Firestore

## Local Setup

### 1. Install dependencies

```bash
cd backend
npm install
```

### 2. Configure Firebase credentials

Set these in the terminal before starting the backend:

```bash
export GOOGLE_APPLICATION_CREDENTIALS="/absolute/path/to/your-firebase-admin-key.json"
export GCP_PROJECT_ID="your-firebase-project-id"
```

### 3. Start the backend

```bash
node backend/server.js
```

### 4. Verify backend connectivity

Open:

```text
http://localhost:8080/health
```

You want to see:

```json
{
  "status": "ok",
  "service": "bustler-backend",
  "mode": "firestore"
}
```

## Local Test URLs

### Customer view

```text
http://localhost:8080/index.html?user_id=usr_customer_1&role=customer
```

### Provider view

Use the link generated by the customer app. For local testing it includes the assigned provider ID automatically.

Example:

```text
http://localhost:8080/provider.html?token=YOUR_TOKEN&user_id=usr_provider_1&role=provider
```

## Recommended Demo Flow

1. Open the customer page.
2. Enter or confirm:
   - current user ID
   - assigned provider ID
   - optional product/order ID
3. Generate a brief from typed or random feedback.
4. Approve and send.
5. Open the generated provider link.
6. Mark the brief `In Progress`.
7. Mark it `Completed`.
8. Return to the customer view and request a further revision.
9. Re-send the updated brief.
10. Reuse the same provider link for the next revision round.
11. Conclude the brief from the customer side after final completion.

## What Bustler Should Replace In Production

This prototype uses URL params and local session simulation for testing. In production, Bustler should replace that with real authenticated session data.

Bustler should inject a context object like:

```html
<script>
  window.BUSTLER_CONTEXT = {
    currentUserId: "usr_customer_123",
    currentUserRole: "customer",
    assignedProviderId: "usr_provider_456",
    productId: "order_789"
  };
</script>
```

For the provider page:

```html
<script>
  window.BUSTLER_CONTEXT = {
    currentUserId: "usr_provider_456",
    currentUserRole: "provider"
  };
</script>
```

## Things To Change Before Production

- Replace local session simulation with Bustler’s real authenticated session injection.
- Replace local test URLs with normal app routes.
- Move this backend logic into Bustler’s existing backend if preferred.
- Store secrets only in environment variables, never in source code.
- Tighten Firestore/IAM setup for production deployment.
- Review copy and generated content behavior around live xAI/Grok usage before release.

## Important Notes

- Do not commit Firebase admin JSON keys.
- Do not commit real API keys or private credentials.
- GitHub Pages alone is not enough for this app because access control depends on a backend.

## Known Prototype Constraints

- Local testing still simulates Bustler login with `user_id` and `role`.
- The generated provider link includes provider identity params only for local testing convenience.
- In production, token access should rely on Bustler-authenticated sessions rather than public query params.
